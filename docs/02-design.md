## 2. 외부 API

### 2.1 Open-Meteo Forecast
`GET https://api.open-meteo.com/v1/forecast?latitude={lat}&longitude={lon}&current=temperature_2m,apparent_temperature,weather_code,wind_speed_10m&daily=temperature_2m_max,temperature_2m_min,precipitation_probability_max,precipitation_sum,weather_code&timezone=auto`

### 2.2 Open-Meteo Geocoding (도시 검색) — **v1.2에서 제거됨**
`GET https://geocoding-api.open-meteo.com/v1/search?name={query}&count=5&language=ko`

> 한국 전용 서비스로 방향을 잡으면서(FR-02/FR-13) 전국 시·군 161곳을 `data/regions.ts`에 내장하고
> 이 API 의존을 걷어냈다. 네트워크 호출 하나가 줄고, 검색 결과에 해외 동명 도시가 섞이는 문제도 사라졌다.

### 2.3 WMO weather_code 매핑
| 코드 | 상태 | 아이콘 |
|---|---|---|
| 0 | 맑음 | ☀️ |
| 1–2 | 대체로 맑음/구름 조금 | 🌤️ |
| 3 | 흐림 | ☁️ |
| 45,48 | 안개 | 🌫️ |
| 51–57, 61–67, 80–82 | 비 | 🌧️ |
| 71–77, 85–86 | 눈 | 🌨️ |
| 95–99 | 뇌우 | ⛈️ |

## 3. 데이터 모델

```ts
type TempBand = 'freezing' | 'cold' | 'chilly' | 'mild' | 'warm' | 'hot';

interface WeatherSummary {
  city: string;
  tempNow: number;        // 현재 기온 ℃
  feelsLike: number;      // 체감 온도 ℃
  tempMin: number;
  tempMax: number;
  precipProb: number;     // 강수확률 최대 %
  precipSum: number;      // 일 강수량 mm
  windSpeed: number;      // km/h
  weatherCode: number;    // WMO code
}

type StyleId = 'oldmoney' | 'casual' | 'formal' | 'minimal';

interface Outfit {
  id: string;
  style: StyleId;
  bands: TempBand[];      // 이 코디가 적합한 기온대
  name: string;           // 코디 이름 (예: "네이비 블레이저 클래식")
  items: {                // 아이템 구성
    outer?: string;
    top: string;
    bottom: string;
    shoes: string;
    acc?: string;
  };
  tip: string;            // 스타일링 팁
  rainOk: boolean;        // 강수 시에도 무난한가 (스웨이드 등 취약 소재 여부)
  palette: string[];      // 코디 대표 색 3~4개 (hex) — 카드에 색 견본으로 표시
}
```

## 4. 추천 룰 엔진 설계

### 4.1 기온대(TempBand) 판정
기준 온도 = `(오늘 최고기온 + 체감온도) / 2` — 아침에 봐도 낮 기준으로 입도록 최고기온에 가중.

| Band | 기준 온도 |
|---|---|
| freezing | < 0℃ |
| cold | 0 ~ 8℃ |
| chilly | 9 ~ 16℃ |
| mild | 17 ~ 22℃ |
| warm | 23 ~ 27℃ |
| hot | ≥ 28℃ |

### 4.2 필터링·정렬 규칙
1. 카테고리·기온대가 일치하는 코디를 후보로 뽑는다.
2. **강수 규칙**: 강수확률 ≥ 60% 또는 강수량 ≥ 1mm면 `rainOk: false` 코디는 후순위로 밀고 경고 뱃지를 단다(제거하지 않음 — 선택지는 유지).
3. 날짜 기반 시드로 섞어 **매일 다른 순서**로 보여준다 (같은 날은 순서 고정 → 새로고침해도 안 바뀜).
4. 대표 추천 = 기본 카테고리(올드머니) 후보 1순위.

### 4.3 날씨 조언(Advice) 규칙
| 조건 | 조언 |
|---|---|
| 강수확률 ≥ 60% 또는 비/뇌우 코드 | "우산 챙기세요" + 방수 신발 권장 |
| 눈 코드 | 미끄럼 주의, 방한 부츠 |
| 일교차(최고-최저) ≥ 10℃ | 레이어링(겉옷 탈착) 권장 |
| 체감 ≤ -10℃ | 한파: 목도리·장갑·히트텍 |
| 체감 ≥ 33℃ | 폭염: 통기성 소재, 밝은 색 |
| 풍속 ≥ 30km/h | 강풍: 모자·가벼운 아이템 주의 |

## 5. 코디 데이터 설계

- 4개 스타일 × 6개 기온대를 모두 커버, **기온대·카테고리 조합마다 최소 2개** (FR-05).
- 코디는 `bands`에 인접 기온대를 복수 지정 가능 (예: 니트 코디 = cold+chilly).
- 총 40여 개 코디를 `data/outfits.ts`에 정적 데이터로 작성.
- 페르소나(20대 후반 남성, 깔끔함 선호)에 맞게 색은 뉴트럴 중심.

## 7. 용어 풀이 · 대체제 설계 (v1.1, FR-10/11)

```ts
interface GlossaryEntry {
  term: string;        // 아이템 텍스트에서 부분 일치로 찾는 용어
  fields?: (keyof OutfitItems)[]; // 동음이의어 구분 (예: '옥스포드'는 shoes에서만 구두)
  meaning: string;     // 일반인 눈높이 설명
  sub: string;         // 없을 때 대체제 안내
}
```

- `src/data/glossary.ts`에 정적 데이터로 관리. 매칭은 **긴 용어 우선**(예: '옥스포드 셔츠'가 '옥스포드'보다 먼저), 이미 매칭된 구간은 중복 매칭하지 않는다 (`findGlossary()` 순수 함수 — 테스트 대상).
- UI: 코디 카드 하단 "쉽게 풀이 · 대체 아이템" 토글 → 각주 스타일 패널에 `용어 — 설명 (없으면: 대체제)` 목록 표시. 호버 툴팁은 iPhone에서 쓸 수 없으므로 탭 토글 방식.

## 8. 대안 코디 규칙 (v1.1, FR-12)

- 현재 기온대의 **인접 기온대(±1)** 코디를 대안으로 제공한다.
  - 더운 쪽 인접 밴드 → "더 시원하게 입고 싶다면"
  - 추운 쪽 인접 밴드 → "쌀쌀하게 느껴진다면"
- 본 추천에 이미 나온 코디(밴드가 겹치는 코디)는 대안에서 제외한다.
- 최저/최고 밴드(freezing/hot)에서는 한쪽 대안만 존재한다.
- UI: 본 추천 아래 "대안 코디 더 보기" 토글 섹션. 카드 번호는 `ALT 01…`로 구분.

## 9. 한국 지역 데이터 설계 (v1.2, FR-13)

- `src/data/regions.ts`에 **대한민국 전역 시/군 좌표를 정적 내장** — 외부 지오코딩 API 의존 제거.
- 구조: `{ province: string; cities: { name; latitude; longitude }[] }[]` — 17개 시·도.
- 광역시(서울·부산·대구·인천·광주·대전·울산·세종)는 단일 지점: 도심 구 단위는 기상 차이가 무의미하고 좌표 오류 위험만 커짐.
- 도 단위는 전 시/군 수록 (경기 31, 강원 18, 충북 11, 충남 15, 전북 14, 전남 22, 경북 22, 경남 18, 제주 2).
- UI: 네이티브 `<select>` + `<optgroup>` 2단 구조 한 개 — iPhone에서 휠 피커로 열려 접근성·모바일 UX가 커스텀 드롭다운보다 낫다.
- 기존 Open-Meteo 지오코딩 검색(해외 포함)은 제거. Forecast API 호출은 동일.

## 10. 쿨톤 스타일 방침 (v1.2, FR-14)

- 코디 색상 원칙: **베이스 = 네이비·차콜·그레이·화이트·블랙**, 포인트는 코디당 1곳(아이스블루·스틸블루·페일그레이 등 차가운 계열, 소재·실루엣 포인트 포함).
- 금지: 강렬한 원색, 웜톤 주조색(캐멀·버건디·머스터드 주조), 화려한 패턴.
- 데이터 반영: `Outfit.point` 필드 신설 — 이 코디의 "조용한 포인트"가 무엇인지 한 줄 명시, 카드에 표시.
- 앱 UI 테마도 웜 크림 → **쿨 포슬린**(한지 느낌의 차가운 회백지 + 딥네이비·스틸블루 잉크)으로 전환.

## 11. v1.4 설계 추가 — 색상 시각화 (FR-19)

**문제**: 카드에 색이 이름(텍스트)과 작은 팔레트 스와치 4개로만 있어, 어떤 색이 상의고 어떤 색이 하의인지
연결되지 않았다. "입어보기 전까지 느낌이 안 온다"는 피드백.

**해결**: 아이템 텍스트에서 실제 색을 추출해 옷 모양(사람 형태 아님, 셔츠·바지·신발의 단순 픽토그램)에
그대로 칠하는 미니 실루엣.

- `data/colors.ts`: 색 이름 키워드(28종, 라이트그레이·다크네이비 등 구체적 키워드가 그레이·네이비 같은
  일반 키워드보다 먼저 매칭되도록 길이 내림차순 정렬) → hex 매핑. `extractColor(text, fallback)` 순수 함수.
  - "동일 톤/원단"처럼 색 이름이 없고 앞 아이템 색을 참조하는 문구는 호출 측(컴포넌트)이 상의 색을
    fallback으로 넘겨 자연스럽게 이어받는다.
  - "저먼 트레이너"·"고무창" 등 색 이름 없이 관용적으로 색이 정해지는 신발 문구는 예외 키워드로 등록.
- `components/OutfitSilhouette.tsx`: viewBox 100×132 SVG. 상의(몸판+소매), 아우터(있으면 열린 코트처럼
  양옆 패널만 덮어 가운데로 상의색이 비치게), 하의(다리 두 개), 신발(발 두 개) — 총 4개 부위를 각 아이템의
  실제 색으로 채운다. 테두리는 `var(--line-strong)`로 얇게 둘러 밝은색끼리 붙어도 형태가 구분되게 한다.
- 배치: 카드 안에서 실루엣(고정폭 78px)과 아이템 텍스트 목록을 가로로 나란히 — "썸네일 + 상세 목록" 구조라
  쇼핑 앱과 비슷한 익숙한 패턴. 기존 팔레트 스와치 UI는 제거하되, `Outfit.palette` 데이터 필드 자체는
  쿨톤/웜톤 검증 테스트용으로 계속 유지한다(더는 렌더링하지 않을 뿐).
- 데이터 품질 게이트: outer/top/bottom/shoes 텍스트는 알려진 예외(2~3개 "동일 톤" 문구)를 빼면 전부
  색 키워드를 포함해야 한다는 테스트를 두어, 앞으로 코디를 추가할 때 실루엣이 회색으로 뭉개지는 걸 방지.

## 12. v1.3 설계 추가

### 12.1 톤 모델 (FR-14/15)
- `Outfit.tone: 'cool' | 'warm'` 필드 신설. 기존 43벌은 cool, 웜톤 코디를 별도 추가.
- 팔레트 검증 규칙 분리: cool은 기존 규칙(R−B≤10) 유지, warm은 완화(R−B≤100)하되 **고채도 원색 금지(채널차≤100)는 공통**.
- `recommend()`에 톤 필터 인자 추가. '전체'일 때 쿨톤 우선 정렬(안정 정렬로 시드 순서 유지).

### 12.2 아이템 아이콘 (FR-16)
- 사진 대신 **인라인 SVG 라인 아이콘**: 저작권·용량·로딩 문제가 없고 쿨톤 테마 색을 그대로 따른다(`stroke: currentColor`).
- 아이템 텍스트 키워드 → 아이콘 매핑 (`components/ItemIcon.tsx`의 순수 함수 `pickIcon(field, text)` — 테스트 대상):
  - outer: 패딩/다운→패딩, 코트/트렌치/발마칸/맥/체스터필드→코트, 그 외→자켓
  - top: '반팔'·'피케 폴로' 포함→반팔, 셔츠→셔츠, 니트/터틀넥/맨투맨/후디/가디건→니트, 그 외→긴팔
  - bottom: 쇼츠/버뮤다→반바지, 그 외→긴바지
  - shoes: 부츠→부츠, 샌들→샌들, 스니커/트레이너/슬립온→스니커, 그 외→구두
  - acc: 모자/캡/햇→모자, 백/토트/사코슈/브리프→가방, 시계→시계, 머플러→머플러, 그 외→장갑 겸 범용

### 12.3 일일 브리핑 엔진 (FR-17)
- Forecast API에 `hourly=temperature_2m,apparent_temperature,precipitation_probability,weather_code` 추가 (24h).
- `engine/briefing.ts` (순수 함수, 테스트 대상):
  - 시간대 구분: 아침 6–11시 / 낮 11–17시 / 저녁 17–22시 — 각 구간 대표 기온(평균)
  - 강수 구간 탐지: 확률 ≥ 50%가 연속되는 시간 구간 → "오후 2시~6시 비 예보 — 외출 시 우산"
  - 기온 흐름 문장: "아침 24° → 낮 31° → 저녁 27°" + 일교차 시 겉옷 조언
  - 추천 기준 온도도 **활동 시간대(9–21시) 평균 체감**을 반영해 하루 전체에 적합하게 보정
- **LLM 미사용 결정**: LLM API는 키·서버가 필요해 NFR-03(키 없는 정적 앱)과 충돌. 동일한 사용자 가치(하루 요약·행동 조언)를 룰 기반으로 제공. 추후 서버리스 프록시를 두면 LLM 요약으로 교체 가능하도록 브리핑을 문자열 배열 인터페이스로 분리.
- UI: 날씨 카드 아래 `DayBrief` — 아침/낮/저녁 3칸 + 24시간 기온 스파크라인(SVG) + 브리핑 문장.

## 14. v1.8 설계 개정 — 의류 에셋 전면 재작도 + 시간 인식

### 14.1 왜 다시 그렸나 (FR-16/19 개정)

v1.7까지는 코디 실루엣에 game-icons.net 에셋을 가져다 색만 입혔다. 전수 QA에서 다음이 드러났다.

| 문제 | 영향 |
|---|---|
| `shirtButton` 에셋이 셔츠가 아니라 **바느질 단추** 그림이었다 | 아우터 없는 셔츠 코디 6벌의 상의가 동그란 단추로 표시 |
| 상의 판정에 '수트' 키워드가 없어 뒤에 붙은 '셔츠'·'니트'가 이겼다 | 포멀 5벌의 정장이 후드티·단추로 표시 |
| 니트 계열을 전부 `hoodie`(후드 달린 옷)로 그렸다 | 터틀넥·크루넥 니트 10벌이 후드티로 표시 |

| 에셋마다 원본 여백이 제각각이었다 | 36×20 슬롯에서 구두 5.8px, 샌들 18.4px로 3배 차이 |

에셋 자체가 옷과 어긋나 있어 매핑만 고쳐서는 해결되지 않으므로 **전량 직접 작도**로 대체했다.
부수 효과로 CC BY 3.0 저작자 표시 의무도 사라졌다(v1.7까지는 README에만 있고 배포 페이지엔 없었다).

### 14.2 재발 방지 설계 규칙 (`data/clothingPaths.ts`)

1. **같은 슬롯에 들어가는 에셋은 viewBox를 공유한다** — 상의·아우터 100×118, 하의 100×120, 신발 100×46.
   크기 비율 어긋남(위 5번)은 에셋마다 좌표계가 달랐던 탓이므로, 좌표계를 고정해 구조적으로 막는다.
2. **viewBox 안에서 실제 옷 길이 비율대로 그린다** — 반바지가 긴바지보다 짧고 부츠가 구두보다 높은 건
   의도된 결과다(각 에셋을 슬롯에 꽉 채우지 않는다).
3. **body(채움) + details(구분선) 2층 구조** — body는 코디 색으로 칠하고, 그 위에 라펠·누빔·단추·주머니를
   선으로 얹어 코트/패딩/자켓/가디건/셔켓/수트를 구분한다. 색만으로는 종류를 구분할 수 없기 때문.
4. **상의·아우터는 같은 골격**(목선 x41~59 / 어깨점 (27,13)·(73,13) / 몸통 옆선 x29·x71)을 쓰고,
   details의 암홀 두 줄로 소매와 몸통을 가른다 — 없으면 어깨가 넓은 판때기로 보인다.

### 14.3 색 대비 처리

- **디테일 선**: 채움색의 밝기(BT.601 근사)를 재서 밝으면 검은 선, 어두우면 흰 선을 얹는다.
  블랙 코트에 검은 라펠선을 그리면 안 보이기 때문.
- **외곽선**: 채움색이 아니라 `currentColor`(글자색)를 옅게 쓴다. 화이트 스니커·오프화이트 슬랙스가
  배경과 밝기가 비슷해 통째로 사라지던 문제를 라이트/다크 테마 양쪽에서 함께 해결한다.
- 에셋마다 축척이 달라도 선 두께가 같아 보이도록 `vector-effect="non-scaling-stroke"`를 쓴다.

### 14.4 배치 로직 분리 (`engine/silhouette.ts`)

공유 이미지(FR-34)가 화면과 같은 그림을 그려야 하므로 "무엇을 어디에 어떤 색으로"만 순수 함수로 떼어,
React 컴포넌트와 PNG 렌더러가 공유한다. 한쪽만 고쳐 둘이 달라지는 사고를 막기 위한 분리다.

### 14.5 시간 인식 추천 (FR-28)

`daytimeFeels(w, nowHour)` / `referenceTemp(w, nowHour)`에 현재 시각을 **주입식**으로 넘긴다
(`Date.now()`를 엔진 안에서 읽으면 순수성이 깨져 테스트가 시간에 흔들린다).

- 기준 구간 = `[max(now, 9), 21)`, 21시 이후면 `[now, 24)`로 폴백.
- **17시 이후엔 하루 최고기온을 섞지 않는다** — 이미 지나간 한낮 기온이 섞이면 밤에 얇게 입히게 된다.
- App은 1분 간격 타이머로 "시(hour)와 날짜가 바뀔 때만" 상태를 교체한다. 매분 리렌더를 피하면서
  자정 넘김(날짜·추천이 어제로 굳던 문제)과 저녁 전환을 동시에 해결한다.

### 14.6 서비스워커 캐시 전략 분리

- **캐시 우선**: 해시가 박힌 `/assets/` 번들, 아이콘, 폰트 CDN — URL이 같으면 내용도 같으므로
  재방문 때 네트워크를 기다릴 이유가 없다(v1.7은 전부 network-first라 항상 대기했다).
- **네트워크 우선**: HTML, Open-Meteo 응답 — 최신이 우선이되 오프라인이면 마지막 값이라도 보여준다.
- 폰트 CDN을 캐싱 대상에 포함해 오프라인에서 브랜드 서체가 깨지던 문제를 해결. `index.html`은
  `media="print" onload` 패턴으로 서체 스타일시트를 렌더 블로킹에서 제외한다(NFR-02).

### 14.7 날짜 인덱스 방어 (FR-30/31)

`past_days=1`을 붙이면 응답 배열 앞에 어제가 끼어들어 "0번이 오늘"이라는 가정이 통째로 어긋난다.
고정 오프셋 대신 **날짜 문자열로 오늘 위치를 찾는다**(`findDayStart`). 날짜 배열이 없는 구버전
응답이나 테스트 목에서는 기존 동작(0번)으로 폴백해 하위 호환을 유지한다.

## 15. v1.9 설계 개정 — 날짜 선택 · 색 조합 · PC 레이아웃

사용자 피드백 세 가지에 대한 응답이다.
"다른 날짜 코디도 보고 싶다" / "어떤 상하의 색 조합이 좋은지 알고 싶다" /
"PC에서 코디가 작아 한눈에 느낌이 오지 않는다".

### 15.1 날짜 전환 (FR-35)

**설계 원칙: 분기를 화면마다 심지 않고 한 지점에서 갈아 끼운다.**

화면과 추천 엔진 전체가 이미 `WeatherSummary` 하나를 기준으로 돈다. 그래서 컴포넌트마다
"오늘인가 아닌가"를 따지는 대신, **선택한 날짜를 WeatherSummary로 다시 포장하는 함수 하나**
(`engine/dayView.ts`의 `weatherForDate`)를 두었다. 코디 추천·조언·브리핑·기온대 판정이
오늘과 같은 규칙 그대로 다른 날짜에 적용되고, 규칙이 갈라질 여지가 없다.

- `WeatherSummary.days[]` — **0번이 오늘**인 7일치. 각 날짜의 시간별 예보를 함께 담는다.
  하루 대표 기온을 최고·최저 중간값으로 때우지 않고 **활동 시간대 평균 체감**으로 잡기 위해서다
  (기존 주간 예보 `week[]`은 오늘을 포함하지 않아 이 용도로 쓸 수 없다).
- 오늘을 고르면 **원본 객체를 그대로 반환**한다(`=== base`). 현재 기온·대기질·어제 비교가 살아야 한다.
- 다른 날은 **오늘 전용 정보를 일부러 떨어뜨린다** — 실측인 현재 대기질을 사흘 뒤 카드에
  붙여 두면 예보처럼 읽혀 잘못된 정보가 된다. "오늘 입었어요"(FR-32)도 같은 이유로 달지 않고,
  기온 그래프의 "지금" 점도 오늘에만 찍는다.
- 바람은 **떨어뜨리는 대신 갈아 끼웠다**: `wind_speed_10m_max`를 일별로 받아 그날 값을 쓴다.
  현재 풍속을 그대로 이어받았더니 지금 부는 바람으로 닷새 뒤 강풍 조언이 붙었다 (QA).
  예보에 없으면 NaN — 조언의 `>= 30` 비교와 화면 표시 양쪽에서 조용히 빠진다.
- 겹 조언은 **기온을 함께 본다**: 35°→31°인 한여름 날에 "겉옷을 하나 더"라고 하지 않도록
  `LAYERING_MAX_TEMP`(25℃) 위에서는 차이만 말한다. 같은 결함이 `yesterdayLine`(FR-30)에도
  있어 함께 고쳤다.
- 추천 시드에 날짜를 넣어(`seedKey = 선택 날짜`) 날짜마다 순서가 달라지게 했다.
- "앞으로 남은 시간" 보정(FR-28)은 **오늘에만** 적용한다. 모레 코디를 지금 시각으로 좁히면 안 된다.
- 고른 날짜가 새로 받은 예보 범위에 없으면(자정 넘김·지역 변경) 조용히 오늘로 되돌린다.

접혀 있던 주간 예보(FR-31)는 **날짜 선택 스트립에 흡수**했다. 예보를 읽는 행동과 그날 코디를
보는 행동이 원래 같은 행동("모레 뭐 입지")인데 화면이 나뉘어 있었다. `week[]` 필드와 수집 코드도
함께 걷어냈다 — `days[]`가 같은 자료를 더 정확하게 담고 있어, 남겨 두면 같은 사실의 출처가 둘이 된다.

### 15.2 색 조합 판정 (FR-36)

**설계 원칙: 조합표를 적지 말고 규칙을 적는다.**

15색이면 225칸이고 색 하나를 늘릴 때마다 31칸이 늘어난다. 손으로는 유지되지 않는다. 더 중요한
이유는 **돌려줄 답이 "좋다/나쁘다"가 아니라 "왜 그런지"여야** 한다는 것 — 규칙으로 만들면
판정과 이유가 자동으로 같은 근거를 가리킨다.

`data/colorFamilies.ts` — 색을 세 축으로만 기술한다. 옷에서 실제로 눈에 띄는 순서이기도 하다.

| 축 | 값 | 비고 |
|---|---|---|
| `value` 명도 | 0~100 | **hex에서 계산한다.** 손으로 적으면 색을 바꿨을 때 조용히 어긋난다 |
| `chroma` 채도 | none / low / mid | 강렬한 원색을 다루지 않으므로 high는 없다 (FR-14) |
| `tone` 계열 | cool / warm / neutral | 무채색은 어느 쪽과도 섞인다 |

`engine/colorPairing.ts` — 위 세 축으로 점수를 매기고, 같은 판단 근거를 문장으로 뱉는다.

1. **명도차** — 가장 크게 작용한다. 40 이상 +3 / 20 이상 +2 / 10 이상 +1 / 미만 −2.
   단 같은 색끼리는 셋업으로 인정(+1).
2. **색의 개수** — 무채색끼리 +1, 한쪽만 유채색이면 그 자리가 포인트가 되므로 +2.
   둘 다 유채색이면 같은 계열 +1(둘 다 채도가 세면 0), 다른 계열 −1(둘 다 세면 −3).
3. **미묘한 어긋남** — 같은 계열의 다른 색을 비슷한 밝기로 붙이면 −2.
   "맞춘 게 아니라 잘못 맞춘 것"처럼 보이는 실패(네이비 상의 + 데님 하의)를 잡는다.

점수 4 이상 `best` / 2 이상 `good` / 그 외 `careful`. 현재 225칸 분포는 102 / 64 / 59다.

- **정석 조합**(흰 셔츠 + 네이비 등)은 등급을 끌어올리지 않고 설명만 덧붙인다. 규칙이 뒤집히면
  규칙을 못 믿게 된다. 규칙이 `careful`로 본 조합은 정석 목록에 넣지 않는다(테스트로 강제).
- `nearestFamily(hex)` — colors.ts의 28개 색 이름을 15칸으로 접는다. 이름 대응표를 손으로 관리하면
  색을 추가할 때 빠뜨리므로 자동 매칭하되, **RGB 거리에 "색기(무채색인가)" 가중치를 얹었다**.
  순수 거리만 쓰면 `#d9dde2`(페일그레이)가 눈에는 명백한 회색인데 아이스블루 칸에 들어간다.
- 판정 결과는 코디 "크게 보기"에도 붙는다 — 추천된 코디의 색 조합이 왜 성립하는지 같은 엔진으로 설명한다.

**신발은 규칙을 따로 둔다 (FR-38).** `judgeShoes(top, bottom, shoes)`를 `pairColors`와 합치지 않은
이유는 **신발이 면적이 작고 맨 아래에 있기 때문**이다. 같은 밝기 차이라도 상하의에서는 "갈라져
보이는가"의 문제지만 신발에서는 "아래가 잡히는가"의 문제이고, 색이 하나 더 붙는다는 점에서 개수
계산도 달라진다. 한 함수에 욱여넣으면 두 규칙이 서로를 갉아먹는다.

신발 규칙에만 있는 세 가지 예외 — 셋 다 없으면 현실에서 가장 흔한 조합들이 경고로 떨어진다.

| 예외 | 없으면 생기는 일 |
|---|---|
| **가죽 색은 계열 충돌에서 면제** (브라운·캐멀·버건디) | "네이비 슬랙스 + 브라운 구두"가 쿨웜 충돌로 '조심해서'가 된다. 남성 구두의 기본 가죽 색이라 눈이 이걸 계열로 읽지 않는다 |
| **밝은 무채색은 밝기 감점에서 면제** | 흰 스니커가 어두운 하의와 만날 때마다 감점된다 |
| **밝은 저채색(크림·오트밀·베이지)은 색으로 세지 않음** | 내장 코디 75벌 중 6벌이 "크림 니트 + 네이비 팬츠 + 브라운 구두"로 "색이 셋"에 걸렸다 (QA) |

신발 색은 15색 전부가 아니라 **11색**만 내놓는다 — 내장 코디가 실제로 쓰는 색(블랙 34 · 브라운 17 ·
화이트 15 · 네이비 6 · 그레이 3)에 흔한 몇을 더한 범위다. "아이스블루 구두" 같은 선택지를 만들지 않는다.

엔진과 데이터를 맞대는 검증을 회귀 테스트로 고정했다: **내장 코디 75벌은 자기 신발 색에 경고를 받지 않는다.**
처음엔 9벌이 걸렸고, 그중 6벌이 같은 패턴이라 데이터가 아니라 규칙이 틀렸다는 신호였다.
- `careful` 등급인데 내장 코디가 그 조합을 쓰는 경우가 있다(소재·겉옷으로 갈라 놓은 경우).
  같은 화면이 서로 다른 말을 하지 않도록 왜 성립하는지 한 줄로 밝힌다.

### 15.3 PC 레이아웃 개편 (FR-37, NFR-01)

원인은 단순했다. **1000px에서 3열로 갈라 카드가 330px까지 좁아졌고, 그 안에서 실루엣이 78px로
줄었다.** 옷 종류는 읽혀도 인상은 전달되지 않는 크기다.

- **화면이 넓어질 때 열을 늘리기 전에 카드를 키운다.** 2열 분기를 720px → **880px**로 올리고,
  3열은 1500px 이상에서만 쓴다. 720px에서 나누면 카드가 332px가 되어, 실루엣을 키운 만큼
  아이템 문구가 밀려 네 줄로 쪼개진다 — 모바일에서 이미 한 번 고쳤던 문제다.
- 실루엣: 78px → 104px(880~) → **152px**(1100~). 본문 폭도 1040 → 1180 → 1460px로 단계적으로 넓힌다.
- **색 팔레트 띠**를 카드에 추가했다. 실루엣은 "어떤 옷인지"에 답하지만 옷 모양에 가려 색 자체는
  작게 보인다. 작은 카드에서도 색 조합이 먼저 읽히게 하는 장치다.
- **크게 보기**(`OutfitDetail`) — 목록은 훑기 위한 것이고 이 창은 한 벌을 제대로 보기 위한 것이다.
  실루엣 240px + 팔레트 + 색 조합 판정(§15.2) + 용어 풀이를 펼친 채로 놓는다.
  제목은 창 맨 위에 둔다 — 두 칸이 모바일에서 세로로 쌓이며 큰 실루엣이 코디 이름을 화면 밖으로
  밀어냈다 (QA). 실루엣 폭도 `min(240px, 58vw)`로 묶어 좁은 화면에서 세로를 다 먹지 않게 했다.
  목록 안에서 ←/→로 넘길 수 있다. 카드를 하나씩 열고 닫으며 비교하는 동작이 실제로는
  "옆에 걸린 옷을 넘겨 보는" 행동이기 때문이다.
- 접근성: `role="dialog" aria-modal`, Esc 닫기, **Tab 포커스 트랩**, 열 때 포커스 이동 후
  닫을 때 원래 버튼으로 복귀, 배경 스크롤 잠금(닫았을 때 엉뚱한 위치로 가는 것 방지).

### 15.4 중복 제거 — 카드와 상세가 갈라지지 않게

카드와 크게 보기가 같은 내용을 각각 적어 두면 한쪽만 고쳐져 화면끼리 다른 말을 하게 된다.
이 프로젝트가 실루엣(화면 vs 공유 이미지)에서 이미 겪은 문제라, 처음부터 한 곳에 두었다.

- `components/OutfitParts.tsx` — `ItemList` · `PaletteStrip` · `GlossaryPanel`
- `components/ShareButton.tsx` — 3단계 폴백과 스크린리더 알림까지 버튼째
- `components/OutfitSilhouette.tsx` — `PieceSilhouette`(조각 목록을 그대로 그림)를 열어,
  코디 실루엣과 색 조합 미리보기가 같은 그림 코드를 쓴다
- `engine/silhouette.ts` — 조각 배치 좌표를 `SLOT` 상수로 뽑아 둘이 공유

### 15.5 CSS에서 두 번 발목을 잡은 것 (기록)

**순서** — 미디어쿼리와 기본 규칙의 명시도가 같아 순서로 이긴다. 데스크톱 오버라이드를 기본 규칙보다
위에 두었더니 미디어쿼리가 조용히 덮여 실루엣이 78px 그대로였다. 카드 관련 미디어쿼리 블록은
반드시 해당 기본 규칙들 **뒤에** 둔다 (`styles.css`에 주석으로 남김).

**그리드 트랙의 최소값** — `overflow-x: auto` 컨테이너를 두는 것만으로는 넘침을 막지 못한다.
그리드 트랙의 기본 최소값이 `auto`(=min-content)라, 15×15 조합표를 감싼 트랙 자체가 표 크기로
부풀어 375px 화면을 747px 밀어냈다. 한 열짜리 그리드라도 `minmax(0, 1fr)`을 명시해야
안쪽 스크롤 컨테이너가 클립할 기회를 얻는다.
